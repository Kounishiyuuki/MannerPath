## 1. 90日最小化を動かす準備

既存の`scheduled.ts`と`runRetentionMaintenance`を使い、REPORTS_DBだけを処理する。写真/R2は無効のまま。
1回は最大10件ずつ、レポートと冪等receiptの更新は同一batch。90日未満の申請を早期消去する機能ではない。

#385の1日1回では最大10件/日で、1鍵の許容50件/日にも追いつかない。本PRは**ローカルで生成する設定案のみ**を
`2-57/5 * * * *`（UTC、5分ごと）へ変更する。288回/日、名目上2,880件/日の処理枠だが、成功率・CPU・読み取り行数・日次quotaの保証ではない。
複数鍵の将来流入には固定の容量保証をしない。実測で残件が減らなければ受付を停止し、無料枠内の設計を見直す。
同一invocation内でloopを増やさず、既存のbounded passを維持する。課金plan・リソースは追加しない。

承認後の担当者の手順：

1. `production:v1-plan`で設定案を生成する。現在は規約未承認によりexit 2/BLOCKEDが正常。生成だけでは有効化されない。
2. 別承認の隔離stagingで、期限前/期限後・23件超backlog・receipt更新失敗/再実行を確認し、予定間隔・CPU/D1 read/writeの実測を記録する。ローカルテストは実Cronの代用ではない。
3. 本番受付前に担当者がREPORTS_DB migrations/保持cronの実配備・実行と、未完了/失敗・未実行を見られることを確認する。本PRではremote実行しない。
4. 保持cronは**受付を停止しても継続**する。App Attestの停止と保持offを混同しない。
5. 復元/rollback後は受付を閉じたまま保持のstatusと再適用を確認する。古い履歴の復元が最小化を取り消し得る。SQL最小化を暗号鍵破棄や物理消去とは説明しない。

### 公開前の最小設定・確認順序（未実行、本番変更は別許可）

1. 正式規約/権利の承認と移行レビューが済むまで受付を開かない。対象Worker・REPORTS_DBのbinding/schema・現行版・復旧bookmarkを確認する。DB/履歴をGitへ保存しない。
2. 既存`production:v1-plan`が生成する候補をレビュー：`REPORT_RETENTION=cleanup`、`REPORT_RETENTION_CRON=2-57/5 * * * *`、`triggers.crons`にも同じ1件。UTCの毎時02/07/…/57分、1日288回。`monitor`は消去しない。写真storage/R2やsource用Cronを追加しない。今の本番Cron空は未配備の事実である。
3. 許可された隔離環境で期限前/後、23件の複数pass、receipt退役・失敗後再実行・restore後full検査、CPU/D1/1102を確認。ローカル成功をremote証拠にしない。実負荷で無料枠/処理容量が足りない場合、受付を開かず設計を見直す。
4. 別許可で配備する担当は、実設定GET/Triggersで上記Cronとvarsの一致を確認し、反映待ち後の**実行ログ**で`mode=cleanup`とcomplete/remaining、実行間隔・CPU/D1を記録する。ログ原本/私的値は公開Git/CIへ置かず、環境・Worker版・時刻・集計・結果だけを残す。受付停止中も保持を動かせることを確認する。
5. ログは#410で確認したinvocation_logs=falseを維持する案。console/error保存は有効で、設定だけで秘匿済みとはしない。保持処理は固定集計ログ/秘匿例外のみ。未確認のplan・account出力・実保持範囲とGmail設定を確認し、不要な本文/認証値を記録/転送しない運用と一致するまでP04はOPEN。ログ無効化や有料化を今回の必須操作としない。
6. 日次監視担当と初回/90日点検日を記録し、失敗時の受付停止・保持継続手順を確認する。必要な本番許可・P0が揃う前に受付を開始しない。

### Cronの重複・失敗・停止をコードと区別する

| 論点 | 現コードと必要な運用 |
| --- | --- |
| 必要な処理/保護 | `scheduled.ts`→`runRetentionMaintenance`→`applyReportRetention`。REPORTS_DB identity/schema/receipt整合性を確認し、1回最大10件ずつの期限到来申請・rate window・challengeを処理。本文等の最小化とreceipt退役を同一batchにする。復元履歴の物理消去ではない |
| 重複実行 | **分散ロック/leaseによる排他は未実装**。DB batchの原子性、更新条件、receiptの一度だけの退役により再実行に備える。これは同時invocationや重複読取り/課金の防止ではない。運用はCronを1系統だけ設定し、手動cleanupを重ねない。既存再実行/再送競合テストは再利用できるが、実D1で同時Cron排他を検証済みとはしない。重複/長時間実行が実測された場合、受付を保留し、単一実行lease等が必要かを限定判断する |
| overdue | dispatcherは未完了をthrowするためCron画面で失敗に見える場合がある。必ず集計結果を読む。正常なbounded進捗を実障害と同一視しない。2回連続で調査、completeから24時間以上未解消なら受付停止。処理件数/残件が減らない状況を放置しない |
| 実失敗/CPU/未実行 | 実失敗2回連続、1102が1回、確認された連続観測で24時間未実行なら受付停止。単発失敗/不明/古いexportは調査。直近1時間の半数以上でCPU>10msは調査強化で、自動停止とは別。`reports:retention-health`に24時間分と観測範囲を渡す。スナップショットの15分鮮度判定と24時間停止判定を混同しない |
| 通常の受付停止 | 許可された担当の`production:v1-stop`はApp IDを削除して既存鍵も含む受付を閉じ、stopped preflightを行う。単なる新規鍵registration pausedでは既存鍵の送信は止まらない。健全な保持Cronは止めない。**この手順書更新ではコマンドを実行しない** |
| 保持を外すrollback | #399の`productionSteps/rollbackConfigs`を使用。全受付停止→stopped PASS→retention-off版配備→stopped PASS→no-cron triggers適用→20分以上待ち、Triggers空/disabled以外の実行なし/次回なしを人が確認→stopped PASS→明示versionへrollback→App ID不在を再確認。CronはWorker版と独立なので、古い版へ戻す前に外す。途中チェック失敗なら先へ進まない |
| データ復旧 | DB rollback/Time Travelは別許可。復元で古い個人値が戻り得るため、受付は閉じたままschema/receipt full検査・期限到来最小化を再適用し、正常稼働を確認してから別途再開判断。DB/secretの単純削除、原記録の上書きで解決しない |

### 90日ごとの保持見直し：実行チェックと最小記録

**担当=MannerPath運営（受任未確認）**。初回は受付開始前、その後は前回確認から90日以内。日次のCron/相談確認は別に続け、鍵失効・方式変更・相談終結・根拠差替え・非公開・サービス終了時は次回を待たず見直す。

- 認証/失効：現行認証・counter/失効回避防止に必要な項目か。方式終了・不要な識別値がないか。安全な削除が未実装なら、必要対象と対応担当を記録する。鍵失効を消去としない。
- 冪等receipt/skeleton：旧下書きの再受付拒否という目的が続くか。本文fingerprint退役の不整合がないか。protocol終了/移行後も無条件に永久保有しない。削除で旧再送を復活させない。
- 審査/独立確認/監査：採用根拠・未解決相談・操作検証に必要な項目か。不要なURL/handle/参照、終了案件の過剰な複製を選別する。discard/withdrawは消去とは別。
- 問い合わせ：未解決/終了案件を分け、回答経緯を残す必要範囲だけ保持する。不要メール・添付・転送/外部copyを別々に扱い、Gmailのゴミ箱移動と完全な物理消去を混同しない。report IDを含むメールの残存関連付けも確認する。
- 提供者/復元copy：実plan、ログ項目/保持・Logpush/外部copy・閲覧権限の変更、restore/exportsの有無を確認。不明やアクセス拒否は不明と記録し、保持期間を推定しない。
- 結果：区分ごとに「継続が必要な理由」「不要になった部分」「実施/依頼/保留と理由」を決める。不要と決めた処理を次回まで放置せず、期限/担当を決める。必要な処理が未実装なら対象限定P0として管理する。

既存のアクセス制限された運用記録へ**区分ごとに1行**残す。生のID・鍵・本文・メール・私的URLは不要：

`確認日 | 区分 | 目的/継続の具体的理由 | 終了条件の該当有無 | 証拠の内部参照/環境・版 | 不要部分と実施結果または未対応理由 | 担当/次の処置期限 | 次回見直し日`

実設定にアクセスできない場合や未実装の必要措置が残る場合は「未確認/未対応」と書く。署名済み規約や自動削除完了の証明に転用しない。台帳/カレンダーへの初回登録と担当受任は、運営者の実操作として残る。

## 2. 追加費用を使わない監視

最低限は毎日1回、担当者が実Cron履歴/最新ログとD1/CPU利用を確認し、記録を残す。最初の7日は既存の初期運用確認と同時に行う。
確認作業ができない場合は受付開始しない。常時自動通知・有料監視はv1.0の前提にしないが、**定期確認そのものは省略不可**。

`npm run reports:retention-health -- <tail-export.jsonl>`は許可された環境のCloudflare tail JSONLを**オフラインで検査するだけ**。
取得・DB操作・通信は行わない。対象Worker/環境の正しいexportであることは担当者が確認する。ログ原本は公開Git/CI artifactへ保存しない。
Cronイベントの`event.cron`、`eventTimestamp`、`outcome`と`logs[].message`内の固定`reportRetention`結果を検査し、本文・座標・ID・原例外は出力しない。

- `healthy`/exit 0：15分以内に実行されたcleanupがcompleteで全残件0。このexportの最新時点だけの証拠。
- `missing`/`stale`：該当cronなし/15分超。未実行や古い資料を正常0件にしない。
- `failed`/`overdue`/`disabled`/`invalid`：要対応。monitorだけの成功、未来時刻、欠落/不正な結果は正常にしない。
- 同じ出力の`action`/`reason`は、export全体の履歴から停止基準を判定する（[受付開始の準備 §3](../../release/V1_PRODUCTION_INTAKE.md)の表）。`stopIntake`なら受付だけを止め、保持Cronは続ける。

実行しなければ検知しないため、本コマンドだけで独立した自動heartbeat監視が完成したとは扱わない。自動通知はP1、毎日の担当者確認はP0。
現在のtail snapshotがhealthyでも、過去24時間の例外・overdue件数は別に見る。Cron履歴と失敗ログも確認し、健康な後続1回で前の失敗を未発生扱いにしない。

| 状態 | 担当者の対応 |
| --- | --- |
| 残件なし/complete | 時刻・Worker版・環境・結果だけを運用記録へ。個別報告ID/本文は不要 |
| overdueが続く/残件が減らない | 2回連続で調査（受付は止めない）。最後のcompleteから24時間以上未解消なら受付停止。容量/失敗原因を確認 |
| failed/receipt不整合/未実行・stale/無効化 | 本当の失敗が2回連続、1102が1件、または24時間以上未実行なら受付停止。1回だけなら調査。保持は継続。receiptの再生成や任意DELETEで解決しない |
| クォータ/CPU余裕不足 | 受付停止、無料枠内で計画を修正。有料化や写真機能の有効化を自動で選ばない |

## 3. 削除・訂正相談の実行可能な最小手順

1. 既存Supportメールで受け付け、相談内容/対応担当/受付・対応期限をアクセス制限された台帳に記録する。公開Issue/Gitへ個別情報を書かない。
2. 分かる範囲の報告ID・対象場所・相談種別を確認。**IDだけで本人と認定しない**。秘密鍵/認証情報/本人確認書類をメールで要求しない。
   不明なら追加の個人情報を集めず、対象を絞れる最小限の説明を依頼する。
3. 個人の申請の削除/開示と、第三者の個人情報・権利侵害/誤地点の通報を分ける。後者は本人確認不能だけで却下せず、運営者が既存審査で調査する。
4. 前者の本人確認は現状専用経路がない。再install時の復旧・本人認定を約束せず、権限不明のまま開示・削除をしない。
   必要ならプライバシー責任者/法務判断へ引き継ぎ、法令上の請求への可否・理由・実施可能な対応を回答する。『90日待てばよい』で一律拒否しない。
5. 対応可能な操作は、期限到来後の既存最小化、既存の審査/却下・レビュー取り下げ、現地/公式情報による事実再確認。
   **却下・鍵失効は個人情報の消去ではない**。レビュー取り下げはexport/公開済み根拠の全消去でもない。
   `local:reports:erasure-impact`はローカル参照調査に限り、remote確認や本人証明にならない。
6. 早期最小化・完全erase・export済み根拠withdrawal・安全な本人確認が必要な案件は、現コードでは未実装として担当者が限定修正を用意する。
   未実装機能を実行済みと通知せず、原本/監査/receiptの参照整合と権利を壊す手動SQLを案内しない。
7. 回答には行った操作・残るデータ/復元履歴・できないことを区別し、相談の終了を記録。相談台帳自体の保持期限はQ2で承認後に運用へ反映。

これは手動相談受付を実行可能にする手順で、法的な削除権への十分性を認定しない。
必要な権利行使を現機能で履行できないと運営者/法務が判断した場合は、限定修正を**P0**として残す。アプリ内の削除/履歴復旧画面を一律P0にしない。

### 返信のひな型（実施事実に合わせて担当者が選ぶ）

- 受付時：「ご相談を受け付けました。対象と対応可能な範囲を確認します。秘密鍵・認証情報・本人確認書類は送らないでください。次回のご連絡予定日は〔担当者が指定〕です。」
- 確認不能時：「現時点の情報では対象/ご本人との関係を確認できず、開示・削除・復旧の完了をお約束できません。第三者の個人情報や誤掲載の問題は引き続き内容を調査します。」法的請求への最終回答は責任者が判断する。
- 実処理後：「〔実際に行った操作〕を〔確認日〕に確認しました。〔残存記録・履歴等〕は別の取扱いとなります。」最小化を完全消去と言い換えず、未実行の操作は書かない。

## 5. 規約確定後の準備（承認/書き込みはしない）

`python3 scripts/prepare-report-terms.py --document <最終全文.md> --version report-terms.YYYY-MM-DD`
は読み取りだけで最終bytesのSHA-256、API文書予定パス、同名iOS bundle予定パスとチェック項目をJSON化する。
草案/CANDIDATE/MAINTAINER-INPUT/未承認/版不一致は拒否するが、これらの文字がないことは法的承認の証明ではない。
出力は常に`prepared-not-approved`/`requiresOwnerApproval:true`。レジストリ・bundle・Web・ファイルを変更せず、権利を与えない。
Q3の承認後に担当者が同一bytesを両側へ配置し、版/hash/同意要約・config・公開URLを照合する。
草案のbytes/hashや過去同意を変更せず、[既存整合手順](CONSISTENCY.md)と[production plan](../../release/V1_PRODUCTION_INTAKE.md)を使う。

公式仕様（2026-11-05確認）：[Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)、
[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)。UTCスケジュール・Freeの各上限と実測容量を区別する。

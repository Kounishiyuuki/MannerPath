## 1. 保持するデータごとの理由・見直し時期・削除条件

90日の最小化（`services/api/src/reports/retention.ts:51-53`）は、cron が `crons: []` のため**まだどの環境でも動いていない**（P03）。

| データ | 保持理由 | 見直し時期 | 削除・最小化の条件 | 現在の実装 |
| --- | --- | --- | --- | --- |
| 申請本文・指定位置・確認日・`submitter_hash`・施設名/営業時間の自由記述 | 審査と事実確認 | 受信から90日 | `minimize_after` が来たらNULL化。P02-3 に当たる場合は期限前 | 期限後のNULL化はある。期限前の処理は**ない**（§3） |
| 申請の残り（ID・分類・規約版・`redacted_at`） | 受付IDへの回答、審査記録との対応 | 受付開始前、その後90日ごと | サービス終了時、または参照する審査記録がなくなったとき | 削除機能なし。外部キーが単純な DELETE を止める（`erasure-impact.ts` `deleteBlockedBy`） |
| 冪等receipt（digest・退役状態） | 同じ下書きの再受付を拒否する | 90日ごと、protocol を変更するとき | protocol を終了するとき。旧下書きを拒否する別の方法を先に実装する | 最小化と同じ batch で退役する。削除機能なし |
| 端末認証の鍵・失効記録 | 不正送信の防止、失効の迂回防止 | 90日ごと、鍵の失効、方式変更、退会相談、サービス終了 | その認証方式をやめるとき。失効記録は、それを無効にしない方法でだけ消す | 失効はある（消去ではない）。180日での失効は未実装（P1） |
| 審査・独立確認・一括却下・管理監査 | 公開した情報の根拠、争いと操作の検証 | 非公開化・根拠の差し替え・相談の終結時、90日ごと | 目的が終わった項目だけ。公開済みの事実をまとめて消すことはしない | ID・状態・理由のみで、申請本文は持たない。削除機能なし |
| 問い合わせ台帳（内部参照・種別・確認方法・処理・担当・回答日・次回確認日） | 対応中の案件、回答経緯 | 案件の終結時、90日ごと | 終結時に、残す理由がない項目を処理する。一律の期限は設けない | 手作業の台帳（アクセス制限） |
| support メール・添付 | 対応中の相談 | 案件の終結時 | 終結し、台帳に必要事項を移したあとにメールを処理。ゴミ箱と転送先の残りも記録する | Gmail の既存操作。保管・転送の実設定は未確認（P04） |
| ログ・復元copy | 防御・診断・復旧 | 90日ごと | 用途が終わったとき。新しい手動copyは原則作らない | 提供者側の設定は一部未確認（P04） |

## 2. P02-3 既存実装で対応できる範囲

| 対応 | 既存の手段 | 効果 | 限界 |
| --- | --- | --- | --- |
| 影響範囲の調査 | `npm run local:reports:erasure-impact -- rp_...`（`src/reports/erasure-impact.ts`） | 参照・receipt・審査の状態が、件数と状態だけで分かる | 読み取り専用。remote には使えない（本番の参照は別の承認） |
| 利用の制限（未採用） | `reports:moderate decide <id> rejected …` | 審査対象から外す | 本文は90日まで残る |
| 利用の制限（queued/proposed） | `review-withdraw` → `queue <id> discarded` | export されない | 同上 |
| 利用の制限（export済み） | 既存の事実再確認と非公開化（`effect-hold`/`effect-withdraw` 等） | 公開面から外す | 申請の根拠参照は残る |
| 90日での最小化 | `retention.ts` | 本文等をNULL化し、receipt を退役 | 期限前には動かない。cron が未稼働 |

**結論：** 利用を止めることは、既存の手段でできる。期限前に本文を消すことは、既存の手段では**できない**。

## 3. P02-3 追加実装が必要な場合の最小修正案（未実装・法的確認の後に着手）

この案は ADR-0021 §11 の option 2 を、**運営者の判断で行う内容起因の処理**に絞ったもの。

ADR-0021 が退けた「IDだけを根拠にした本人からの請求」には使わない。運営者が申請の内容を確認し、第三者の個人情報が含まれると判断した場合にだけ使う。この区別も法的確認の対象とする。

- **関数：** `src/reports/retention.ts` に `minimizeReportEarly(db, reportId, now, reason)` を1つ追加する。
  - 中身は既存の UPDATE（`:51-53`）と `retireReceiptStatement` を、**その1件にだけ**、同じ `db.batch` で実行するもの。
  - 条件は `WHERE report_id = ? AND redacted_at IS NULL`。`minimize_after` は条件にしない。
  - ID の形式が不正なら throw する（`erasure-impact.ts` の `REPORT_ID` と同じ検査）。
- **reports の schema は変更不要：** `migrations-reports/0001_report_store.sql:233-254` の不変 trigger は、期限前でも、個人列をNULLにして `redacted_at` を入れる1回だけの UPDATE を許可する（§3.1 Q1 で確認）。
- **CLI：** `scripts/report-queue.ts` に `minimize-early <reportId> <decidedBy> <reason>` を追加する。
  - 実行前に `erasureImpact` の結果を表示し、確認を求める。
  - 記録：既存の `admin_review_audit` は `state` が審査状態に限られ（`0008_admin_review_audit.sql` の CHECK）、最小化を記録できない（§3.1 Q2）。
    `state='rejected'`・`reason='privacyRisk'` で代用すると審査判断と誤読されるため使わない。最小の案は、ID・日時・担当・理由区分だけを持つ追記専用の表を1つ足す migration（REPORTS_DB 0012）。
- **テスト：** 期限前の1件だけがNULL化されること、他の申請は変わらないこと、receipt が退役して同じ鍵での再送が410になること、2回目は何もしないこと、不正な ID は throw すること。
- **範囲外：** アプリ内の削除画面、本人証明（ADR-0021 §12.1）、行の削除、DATA_DB の根拠撤回（option 3）、写真（v1.1）。
- **規模の見込み：** 本体約30行、migration 約20行（rollback 付き）、テスト約100行。本番での実行・migration 適用は別の承認とする。

### 3.1 技術調査の結果（2026-11-23、ローカル合成DB、正式実装なし）

使い捨てのテスト（リポジトリ外、`test/support/sqlite-d1.ts` のSQLite）で4件とも pass。

| 問い | 結果 |
| --- | --- |
| Q1 期限前の最小化はtriggerで許可されるか | **許可される。** 期限前の1件だけがNULL化され、`minimize_after` は変わらず、他の申請は不変。2回目の UPDATE は trigger が拒否する |
| Q2 既存の監査表で記録できるか | **できない。** `state='minimized'` は CHECK で失敗。上記の新しい表が必要 |
| Q3 receipt退役と最小化を原子的に処理できるか | **できる（SQLite上）。** 同じ batch の3つ目が失敗すると、本文もreceiptも元のまま。Cloudflare D1 の batch がトランザクションであることは、この環境では未確認 |
| Q4 二重報告防止への影響 | 同じ下書きの再送：receiptは `retired` となり、受付されない（既存の90日最小化と同じ）。ほかに次の影響がある（コード読みのみ）：<br>・**重複候補の検出から外れる**（`community-evidence.ts` `duplicateCandidates` は `redacted_at IS NULL` が条件）。同じ場所への新しい申請は、この件との重複として示されなくなる<br>・**独立した申請者として数えられなくなる**（`spotEvidenceStates`、`submitter_hash` がNULL）<br>・送信回数の制限（`report_rate_windows`）は別の表なので影響しない |

## 4. 運用手順

既存の [OPERATIONS.md §3](OPERATIONS.md#3-削除訂正相談の実行可能な最小手順) 1〜7 をそのまま使い、次を追加する。

1. 受付時に、申請者本人からの請求（P02-2）と、第三者の個人情報・誤地点の通報（P02-1、P02-3）を区別して台帳に書く。
2. P02-3 では、まず §2 の手段で利用を止める。そのうえで、期限前の最小化が必要かを責任者が判断する。
   - 必要で、§3 が未実装のとき：その件を「未対応・限定修正待ち」として台帳に残し、回答テンプレート C を使う。
3. P02-2 では、本人との関係を確認できないまま開示や削除をしない。法的確認の結論が出るまでは、テンプレート B を使う。
4. 終結時に、§1 の表に沿って、残すものと処理するものを台帳に書く。

## 5. 回答テンプレート（実施した事実に合わせて担当者が選ぶ）

[OPERATIONS.md §3](OPERATIONS.md#返信のひな型実施事実に合わせて担当者が選ぶ) の受付時・確認不能時・実処理後の3通に、次を追加する。

- **A 第三者情報の通報（受付）：**「ご連絡ありがとうございます。該当する申請の内容を確認し、必要に応じて利用を止めます。ご本人の確認は求めません。結果は〔予定日〕までにお知らせします。」
- **B 本人との関係を確認できない請求：**「現在の仕組みでは、ご依頼の申請とご本人との関係を安全に確認できないため、開示・削除はお受けできません。申請の内容は受信から90日で自動的に最小化されます〔最小化の稼働後にのみ記載〕。第三者の個人情報などの問題があれば、内容に基づいて対応します。」（最終文面は法的確認後）
- **C 利用は止めたが期限前の消去が未対応：**「該当する申請を〔確認日〕に審査対象から外しました。申請の内容は現在も保存されています。期限前の消去は準備中で、実施したら改めてお知らせします。」
- **D 期限前に最小化した後（§3 の実装後のみ）：**「該当する申請の本文・位置・日付・申請者との関連付けを〔実施日〕に消去しました。受付ID・分類・審査記録は残ります。これは全データの消去ではありません。」

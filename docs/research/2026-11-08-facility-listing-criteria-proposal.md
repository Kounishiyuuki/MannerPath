Status: **Proposal / 未承認・未実装**。調査基準main `6729d56`（PR #400統合後）、2026-11-08。

## 1. 問題の分解

現行SPECIFICATION §2–6 / ADR-0012はcoverage-first、存在と位置の独立、unknown維持を既に要求する。
喫煙固有時間、紙巻き／加熱式、一般客利用、環境のunknownは、公式・運営者事実参照の一律不採用理由ではない。
店舗・施設の存在、たばこ販売、灰皿だけから喫煙許可を推定しない条件は維持する。

現在は以下が同じ「保留」に見えるため、追加余地が判断しにくい。

| 判定軸 | 必要な判断 | unknown / 未完了の扱い |
| --- | --- | --- |
| 喫煙場所の存在・許可 | 対象施設の喫煙場所または喫煙可能な区画を一次情報等で明示確認。現在の禁煙・閉鎖・廃止と矛盾しない | 未確認の場所を作らない。ホストだけでは不合格 |
| 出典の再利用 | 適用規約と権利範囲をsource別に審査 | 未読は未承認。著作権留保だけなら既存D-Rを検討。情報利用・DB化等の明示禁止は解消まで不採用 |
| 所在地 | 施設住所と代表点が同じ施設を指すか、点が何を代表するか | ピン適格、住所のみ候補、未確認を分離する提案 |
| 利用条件 | customer/facility限定、階・区画制限など、記載された条件を保持 | 不明を一般利用可・無料・24時間に変えない。存在が確認済みなら任意項目unknownだけで止めない |
| 取込実装 | source承認、固定fixture、hash、provenance、監視、テスト | adapter未実装は施設不適格と区別する。未実装のまま本番へ出さない |

将来の審査帳票では、軸別のdecision・理由・確認日・根拠URLを記録し、最後に公開判断を行う。
source承認や位置審査を一つのconfidence点数で相殺しない。
既知の禁止・制限をunknownへ落として掲載することも許可しない。

## 3. parcel代表点の条件付き再審査案

現行address-anchor.tsはresidential_detail / residential_blockのみを許容する。これを本PRでは変更しない。
住居表示を用いない住所で、妥当な地番代表点も一律拒否する点には見直し余地がある。
ただし「許容levelにparcelを足す」だけの変更は提案しない。以下をすべて確認する限定経路を別ADRで判断する。

1. **存在は独立確認**: 喫煙設備の事実と施設住所を、適用条件を審査済みの運営者・公式資料等で確認する。ジオコーダーは存在証拠にならない。
2. **完全な住所対応**: 同一市区町村、丁目・本番・枝番まで対応し、未解決剰余なし。町レベル、枝番切捨て、別住所・別施設・曖昧な「付近」は不合格。複数候補から都合の良いものを選ばない。
3. **位置の由来**: 使用したデータ版、ZIP digest、geocoder版・設定、match/coordinate level、座標系またはその既知の制限を保持。位置参照できない任意座標や地図画像から読んだ点を使わない。
4. **地番と施設の同一性・範囲**: 点が同じ地番の代表であることに加え、対象施設へ合理的に案内できることを、再利用条件を確認した公式参照資料・施設代表点・地理資料等で審査する。広大な敷地、複数施設、駐車場・裏山・立入禁止部等の点は地番一致だけでは承認しない。
5. **追加の再利用条件**: ABRのPDLだけでなく、地番マスターに適用される登記所備付地図データの条件も読む。出典・加工表示、提供範囲、再配布条件を記録する。現時点ではその追加条件を承認していない。
6. **表示と案内**: areaApproximate / facilityだけに限定。喫煙室、入口、namedZone、正確な喫煙点へ格上げしない。距離は施設代表点への目安で、施設付近への案内であることを示す。裏口・立入制限等で誤案内の危険が残る場合はピンを出さず住所のみへ回す。
7. **後日の変更**: 正確な設備位置の取得、施設移転、source変更は既存の同一性・relocation審査を経る。自動上書きや新旧二重ピンは作らない。

地番に一律の「誤差50m」等を付ける根拠はない。範囲・施設との対応を検証できない点を、注意書きだけで救済しない。
[ABR利用条件](https://www.digital.go.jp/policies/base_registry_address_tos)は地番マスター・地番マスター位置参照へ追加条件が適用されることを明示する。
同意・適合・位置妥当性の判断を完了するまで、国際ホテル・倉式・満天の座標は公開入力にしない。

## 4. 住所のみの施設検索案

既存TileSpotV1、Spotのcanonical経路、WatchSpot / WatchSnapshotは有限座標が必要。
その座標をnullにする全体変更、0/0・町中心・市役所・近くの別店舗等による穴埋めは行わない。

別の `FacilityListing` resourceを設計する案とする。次は将来の契約例で、現在のAPIではない。

- 型: Spotと別の識別子・discriminated kind、name、運営者の公式住所、行政区域、正規化した設備事実、利用条件、確認日、source/release/record参照、帰属表示。
- 位置: addressOnlyを明示し、緯度経度・tile key・距離・bearing・arrivalを持たない。住所文字列から暗黙に座標を生成しない。
- 公開条件: 存在・利用許可、current-operation、source権利、公開承認のゲートを別resourceにも設ける。未承認intake一覧をそのままAPIへ返さない。閉鎖・廃止・情報利用禁止への対応と撤回履歴も必要。
- 検索: 名称・市区町村・住所で検索。「近く500m」の結果や距離順へ混ぜず、「地域内の施設情報・詳しい位置未確認」等の別セクションに表示する。
- 表示: 「施設内に喫煙設備の記載あり」「詳しい位置は未確認」、確認日と条件。屋内外・紙巻／加熱・営業時間・一般利用の不明は不明と示す。客室階限定等の既知条件は隠さない。
- 操作: 公式案内を見る、住所を確認する。外部地図の住所検索を将来提供する場合も一時的な検索として別設計し、Maps POIをcanonicalへ保存せず、喫煙地点のピンと誤認させない。
- 配信境界: 既存tiles、近傍検索・ランキング・距離・方向・直接経路、PhoneWatchSync snapshot、Watch近傍一覧、iPhone/Watch Widgetへ渡さない。既存Spot DTOと別の型でコンパイル時・実行時に拒否する。
- 昇格: 適格施設点を取得したら別途位置・同一性・重複を審査してSpotへ紐付ける。自動昇格せず、一覧とピンで二重に地点数を数えない。

データ保存はimmutable source/release/recordを参照する専用領域（別テーブルまたはレビュー済みartifact）を比較する。
全国全件をアプリに一括返す設計にはせず、ページング・索引・キャッシュ・撤回の単位をAPI設計時に決める。
既存513地点のSpot ID、座標、タイル本文、ETag、Watch DTOを変更しない方式を優先する。

## 5. 共通取込案

小規模な公式事実参照について、共通adapter factory＋publisher/権利スコープ別の宣言設定・固定fact sheetを提案する。
特殊な自治体CSV等のadapterを一括置換せず、既存SourceAdapterインターフェースを生成物にも守らせる。

維持する境界:

- source ID、registry承認、権利条項・適用範囲、attribution、hold/撤回はpublisher/権利範囲ごとに分離。
- recordごとに設備事実、公式URL、checkedAt、住所、位置根拠、利用条件、フィールドprovenanceを保持。
- レビュー済みの宣言・fixture SHA・許可行列・release URL/確認日・parser/mapping/resolver版を固定。無断改変を拒否する。
- source-healthは設備事実と住所・権利scopeを再確認し、変更は再審査する。初期値partial、crossReleaseValidated=falseを維持。
- 現行のsource holdはsource単位である。publisherが同じという理由だけで全国の施設を一つの停止単位へ統合しない。監視・撤回を独立判断するページ群はsourceを分けて共通処理を使う。record単位のholdへ変える場合は別の設計・ADR・移行審査が必要。
- 共通処理にURL/任意CSVを渡しただけでsourceがapprovedになる仕組みや、全運営者混合の承認済みsourceを作らない。
- 同じpublisherで同じ規約範囲の店舗群は審査を再利用できるが、各店舗の存在・閉鎖・住所・条件の確認は省略しない。

source追加の複数の手作業登録は、一つのレビュー対象manifestから生成・整合検査する設計を検討する。
生成結果のsource identityと承認状態は差分で確認可能にし、runtimeの未知source自動登録はしない。
専用コードの有無を施設の適否と同一視しない一方、共通化を権利審査の代替にしない。

## 6. communityによる追加との関係

既存communityReported / communityVerifiedを活用する方針は維持できるが、現在COMMUNITY_PUBLICATIONはpending。
v1.0の新規申請は、1件の申告・承認済み規約への同意・具体的な喫煙場所の申告・個別審査に加え、
運営者による公式情報／現地の独立確認をnew_spot_evidence_checksへ記録する必要がある。
写真がないことだけを必ずしも拒否理由にしない一方、投稿文だけで公開しない。v1.1写真PoCを再開する提案ではない。
独立した利用者の確認によりcommunityVerifiedへ進める。報告をofficial/operatorへ自動昇格させない。
Web調査を架空の利用者申請へ変換して権利ゲートを回避しない。実際の申請がないため追加件数は見積もらない。
規約・権利要求対応・retention・受付/実機確認・公開承認は、それぞれ既存の承認手続が必要。
